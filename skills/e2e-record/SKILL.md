# 代替 Step1: 録画起点の価値フロー地図化（e2e-record）

人が ChromeDevTools Recorder で「プロダクトの価値となるシナリオ」を1本実演した録画（JSON）を種に、**happy path を1本**確定し、後段（e2e-spec）が周辺テストを起こせる **遷移マップ付き plan** に落とす。**e2e-map の代替 Step1**であり、出力の体裁は e2e-map と揃える（後段 e2e-spec / オーケストレーター e2e-plan にそのまま乗せるため）。

## 核となる思想（再議論しない確定事項）

- **録画は「正確な happy path の種」＝ヒントであって正解データではない。** 録画セレクタは玉石混交（エフェメラルな UUID id・座標依存・深い nth-of-type が混ざる）で、そのままでは再生不能。録画を「ヒント」に降格し、要修復箇所は明示フラグを立てて後段のライブ探索へ送る。
- **品質は人間承認ゲートで担保する。** 「録画に係留＝幻覚ゼロ」は録画がヒントに降格した時点で成立しない。代わりに人間が「これは実演に忠実か・何をもって成功とするか」を承認する。
- **オラクル（成功判定）は WHAT=人間意図／HOW=ライブ探索。** 「何をもって成功とするか（WHAT）」はこの Step で人間に確認する。「どの要素で確認するか（HOW）」は録画からは確定せず「未確定」として残し、後段（ライブ探索）へ送る。
- **permission（別ロール／ログアウト）は視野外。** 録画1本は「1人のユーザーが価値を得る流れ」。権限は別シナリオ。

## MVP 境界（超重要・越えたら止まる）

**この Step は plan.md を出したら止まる。** ライブ探索・要修復セレクタの実解決・オラクル HOW の確定・Playwright コード生成・5観点の派生テスト生成には**踏み込まない**（それらは後段の責務）。境界を越えそうになったらユーザーに確認する。

## まず既存の横断スナップショットを読む（重複回避・未検証優先）

e2e-map と同じく、地図化を始める前にスイート全体の現況を把握し、既に他 feature で検証済みの経路を二重に作らない。

1. **`e2e/index.md` があれば最初に読む**（`/e2e-audit` が再生成する横断 coverage 派生スナップショット。読むだけ・書き換えない）。
2. 無ければ **`e2e/plans/*.md` を直接スキャン**して既存シナリオ（class/role/`coverage` メタ）を素材にする。
3. 録画の経路が既存 feature で検証済みなら、その経路は Step2（e2e-spec）で `status=covered_elsewhere` にする候補として申し送る（どの feature で検証済みかを併記）。
4. 未検証・gap の経路を優先する。

> どちらも無い（初回）場合はこの手順を飛ばし、通常どおり録画起点で地図化する。

---

## 手順（5ステップ）

### 1. 録画JSONを読む

`argument-hint` で受けた JSON パス（ChromeDevTools Recorder のエクスポート）を読む。`title` と `steps[]` を取る。`steps[]` は `setViewport` / `navigate` / `click` / `change` / `keyDown` / `keyUp` の生イベント列。

### 2. 正規化（生イベント列 → 意味ステップ列）

**(2-1) ノイズ除去**

- `setViewport` を落とす。
- **意味のない keyDown/keyUp を落とす**: `ArrowLeft`/`ArrowRight` 等の移動キー、`Meta`/`Control`/`Shift`/`Alt` 単独、**入力取り消し用の単独 `Backspace`**。
- **意味のある確定キーは残す**: タグ入力の確定 `Enter`、フォーム送信の `Enter` など「操作として意味を持つキー」は意味ステップとして残す。
- `keyDown`/`keyUp` のペアや、同一要素への連続 `change` は1操作に畳む。

**(2-2) 意味ステップ化**

残ったイベントを **`navigate` / `click` / `fill`（=`change`）** の意味ステップ列に落とす。`navigate` の `assertedEvents`（遷移後 title 等）は期待結果として拾う。

**(2-3) セレクタ選定（aria/text 優先）**

Recorder は候補をセレクタ配列で吐く（`aria/` / CSS / `xpath/` / `pierce/` / `text/`）。**`aria/…` と `text/…` を優先採用**。位置依存 CSS（`nth-of-type`）・`xpath`・`pierce` は劣後（意味セレクタが無いときの参考にとどめる）。

**(2-4) 要修復フラグ（エフェメラル・位置依存を明示）**

**判定基準（一本化）: `aria/…` / `text/…` が一つも無いセレクタ配列は、原則すべて【要修復】として明示し**、後段のライブ探索で直す前提にする。ここを「正」として plan に確定させない。次の3パターンは、その中でも特に再生不能性が高い・優先度の高い代表例であり、これらに該当しなくても aria/text 不在なら要修復対象から漏らさない。

- **UUID/ランダム id**（例 `#a89f028e-438e-4c80-9da7-849b188fad43`）… 再生不能。
- **座標クリック依存**（`offsetX`/`offsetY` が要素寸法に対して大きい・意味セレクタ無し。例 `offsetX:1268`）… 位置依存。
- **多段（2階層以上）の位置依存 CSS**（`div:nth-of-type(3) li:nth-of-type(2)` 等で aria/text が無いもの）。

> aria/text が併記されていれば要修復ではない（意味セレクタで再生できる）。aria/text が一つも無い時だけフラグを立てる。

**(2-5) ミス入力の検出**

「値を入れた直後に `Backspace` で取り消し、別の値を入れ直す」ような打鍵は**録画者のミス**の可能性が高い（例: `change "tomomi,"` → `Backspace` → `change "tomomi@example.com"`。comma でタグを作って即削除している）。**勝手に採否を決めず**、ステップ3・4の人間確認へ回す。

### 3. 価値フロー vs 後始末を推測して提示 → 人間にラベル付けさせる

**構造だけでは「価値フローのコア」と「後始末（cleanup）」を機械判定できない。** 同じ `delete + はい` が、価値の証明（共有解除）にも片付け（イベント削除・メンバー除去）にも現れる。だから**推測ラベルを提示して人間に確定させる**（自動判定に頼らない）。

- 正規化した意味ステップ列に、推測ラベル（**コア=価値フロー** / **cleanup=後始末**）を付けて提示する。
- 末尾の後始末が多段（例: 詳細画面からのメンバー除去 → イベント本体の削除）に入り組むことがある。**「以降は削除」と雑にまとめず**、区切りごとに推測ラベルを付けて人間に確認させる。
- ステップ2で拾った**ミス入力**（例 `tomomi,`）も「happy path に含めるか」を人間判断に回す。

**この提示はステップ4の `AskUserQuestion` 本文にまとめて含める（別ターンで単独提示しない）。** ここで提示した推測ラベルは、ステップ4の一括質問の一項目として回答してもらう。

### 4. 意図確認（一括質問・推測で決め打ちしない）

e2e-map の「質問はまとめて一括で投げる（1問ずつ往復しない）」流儀に従う。`AskUserQuestion` で次を**一度に**確認する。**推測で決め打ちしない。**

- **機能名／中心価値**: 「これは "〈推測した機能名〉" 機能のテストで良いか？ このプロダクトで価値が成立する中心フローは "〈推測〉" で良いか？」
- **成功の定義（オラクル WHAT）**: 「成功と判断する最終状態は "〈推測。例: 共有相手にイベントが見え、共有解除でメンバーが消える〉" で良いか？」（HOW=どの要素で確認するかは録画からは確定しないので聞かない。未確定として残す）
- **価値フロー vs 後始末のラベル**（ステップ3の推測の承認）: どこまでがコアで、どこからが後始末か。
- **ミス入力の採否**（ステップ2-5・該当時のみ）。
- **再生時の認証方式**: 録画は既ログイン済みの実 Chrome で撮られており**ログイン操作は録画に含まれない**。再生時の `E2E_AUTH_MODE` を確定するため「ログインは**メール＋パスワードを画面入力する形式**か？（はい=`form` / いいえ=`prebuilt-state`（SSO/OTP等）/ 認証不要=`none`）」を必ず聞く。
- **実行ロール名(slug)**: 「このシナリオの実行ロール名(slug)は何か（例: `user`/`admin`）」を聞く。e2e-spec の `coverage.role`（必須フィールド）にそのまま渡すため、ここで確定させる。

### 5. `e2e/plans/<feature>.md` を生成

**feature-name の slug 化はオーケストレーター（`commands/e2e-plan.md`）の規約に従う**（URL は最後の path セグメント採用・空白と予約文字を `-`・連続 `-` 圧縮・日本語は許可）。単独起動でファイル名が曖昧なら slug をユーザーに確認する。

出力は **e2e-map と同じ「遷移マップ」体裁**（後段 e2e-spec が `map#<n>` で参照し、`破壊性` 列で破壊的シナリオを検出するため）に、**録画固有の3節（5観点係留メモ・要修復セレクタ・未確定オラクル HOW）**を足す。下記テンプレート参照。

## 5観点ステップ係留（plan 上の注記まで・実テストは作らない）

正規化した happy path の各ステップを桟橋にして、5観点（validation / network / back / reload / abandon）の**観測点候補を plan に注記する**。**実テスト生成はしない**（それは後段 e2e-spec / e2e-codegen の仕事）。係留先の対応:

| 観点 | 係留先 | 例（イベント共有シナリオ） |
|---|---|---|
| validation | 入力した各欄（`fill`） | 共有相手メール欄に 空／`abc`（非メール）／自分自身 |
| network | 送信系 commit（`click` の送信ボタン） | 「共有する」押下時に 500／オフライン／激遅 → 二重送信・画面崩れ |
| back | 各遷移点（`navigate` / arrow_back） | 共有後に戻ると入力保持されるか・二重共有しないか |
| reload | 各到達画面 | 共有相手入力の途中で F5 → 入力が消える/復元されるか |
| abandon | 破壊的 commit の直前 | 「共有する」直前に離脱 → 中途半端に保存されないか |

**枝刈り基準（総当たりしない＝爆発防止）**

- 全ステップに総当たりしない。**そのステップが意味的にその観点を要求する時だけ**付ける。
- **任意入力欄は validation を刈る**。検証が最も厳しい欄 top-N に絞る。
- **録画に無い画面・分岐へは踏み込まない**（棚卸しに堕ちない）。要修復セレクタのステップも、係留は注記にとどめる（実解決は後段）。

## 守ること

- **plan.md を出したら止まる**（ライブ探索・要修復解決・オラクル HOW 確定・コード生成へ踏み込まない）。
- **コードは書かない。**
- **推測で決め打ちしない**。価値フローのラベル・成功の定義・ミス入力の採否は人間確認へ。未確認は「未確認／未確定」と明記する。
- **5観点の係留は plan 上の注記まで**（実テスト生成はしない）。
- **出力体裁を e2e-map と揃える**。後段 e2e-spec は「遷移マップ」節（`#` 採番・`破壊性` 列）と「未確定（Step2 進行判定）」4項目を読む。ここを崩すと既存パイプラインに乗らない。

## 成果物

`e2e/plans/<feature>.md` に書く（無ければ作成、あれば該当セクションを更新）。**「遷移マップ」節は e2e-map と同一スキーマ**、そのあとに録画固有3節を続ける。

```markdown
# E2E Plan: <表示名>

> 生成日: <YYYY-MM-DD> / 入力源: 録画(ChromeDevTools Recorder JSON: <path>)
> 対象URL: <baseURL/path> / 認証: <再生時方式: form | prebuilt-state | none（ステップ4で確認）>
> 探索環境: ロケール=<例: ja-JP> / タイムゾーン=<例: Asia/Tokyo>

## 意図（人間確認済み）
<機能名 / 中心価値 / 成功の定義WHAT を1〜2文。ステップ4で確定した内容>

## 遷移マップ

### 前提データ / 環境
- ログイン状態: <role。録画は単一ユーザー視点。permission は視野外>
- 必要なシードデータ: <...>
- 除外範囲: <後始末として人間がラベルした範囲・実メール実体 など>

### 画面・遷移表

「破壊性」列＝永続的状態変更＋外部副作用なら種別（作成/更新/削除/送信/課金/メール/通知）、読み取り中心なら `-`。属性の記録であって除外フラグではない（扱いは Step2）。「確認状況」＝録画で実演済みなら `録画実演済`、セレクタ要修復なら `録画実演済(要修復)`、録画外の推測は `未確認`（HOW未確定の行は「録画実演済（オラクルHOW未確定）」等、オラクルHOW節と対応させる注記も併記する）。

**コア/cleanup の区分は列を増やさない**（e2e-map と同一スキーマを保つため）。代わりに、ステップ3で人間確認した cleanup 範囲の**開始行に区切り行**「`--- 以降、後始末（人間確認済み） ---`」を必ず挿入し、行ごとの帰属が失われないようにする。

| # | 画面 | 到達操作 | 分岐条件 | 非同期イベント | 破壊性 | 期待結果 | 確認状況 |
|---|------|----------|----------|----------------|--------|----------|----------|
| 1 | イベント一覧 | `/event-list` へ navigate | - | - | - | title「サーベイイベント一覧…」 | 録画実演済 |
| 2 | 新規作成 | 「新しいイベントを作成する」click `[text]` | - | - | 作成 | 新規イベント項目 | 録画実演済 |
| 3 | イベント名入力 | イベント名 fill `[要validation係留]` | - | - | 作成 | 名称反映 | 録画実演済 |
| 4 | 共有相手入力 | 共有相手 fill `[要validation係留]` ※実メール→パラメタ化(後段) | - | - | - | タグ生成 | 録画実演済 |
| 5 | 共有実行 | 「共有する」click `[要network/abandon係留]` | - | 共有API応答待ち | 送信/通知 | 共有成立 | 録画実演済（オラクルHOW未確定） |
| 6 | 共有解除 | メニュー(`要修復`)→対象メンバー選択→delete→「はい」 | 確認ダイアログ | 解除API応答待ち | 削除 | メンバー消える | 録画実演済(要修復: 行選択が UUID id、メニュー展開が多段nth-of-type) |
| … | `--- 以降、後始末（人間確認済み） ---` | | | | | | |
| 7 | イベント削除 | 対象イベントを開く→delete→「はい」 | 確認ダイアログ | 削除API応答待ち | 削除 | 一覧から消える | 録画実演済 |

### 未確認・要レビュー
- <録画外の分岐・エラー系・権限差分（permission は本モード視野外）>

### 未確定（Step2 進行判定）

Step2（e2e-spec）へ進める契約。4項目のいずれかに「未確定」が残るならオーケストレーターは Step2 に進まず停止する。

- [ ] **中心価値**: 価値を生む中心フローが1文で言えるか（ステップ4で人間確定 → 確定）
- [ ] **ログイン手段**: 再生時 `E2E_AUTH_MODE`（form=メール+パスワード画面入力 / prebuilt-state=SSO等手動採取 / none=認証不要）が確定したか（ステップ4で確認。録画にログイン操作は含まれないので必ず聞く）
- [ ] **対象ロール**: 検証対象ロール（録画は単一ユーザー＝通常1ロール。permission 差分は本モード対象外）が確定したか
- [ ] **画面確認手段**: 録画そのものが実サイト実演＝画面確認済み（→ 確定）。要修復セレクタは「確認済みだが再生には修復要」であり画面未確認ではない

## 5観点係留メモ（後段 e2e-spec 向けの注記・実テストは未生成）

happy path の各ステップに、意味的に要求される観点だけ注記する（総当たりしない）。

- map#3 イベント名 fill → **validation**（空／長すぎ／禁止文字）
- map#4 共有相手メール fill → **validation**（空／`abc`非メール／自分自身）※任意欄なら刈る
- map#5 「共有する」click → **network**（500/オフライン/激遅で二重送信・画面崩れ）, **abandon**（送信直前離脱で部分永続化しないか）
- map#5 到達後 → **back**（戻って二重共有しないか）, **reload**（共有相手入力途中の F5 で入力保持/復元）

## 要修復セレクタ（ライブ探索で解決予定・この Step では直さない）

> **この節（および本テンプレート全体）の内容は例示にすぎない。実行時は必ず対象 JSON の `steps[]` 全体に対して §2-4 の判定基準（aria/text 不在＝原則すべて要修復）を再適用し、テンプレートの記載件数をそのまま流用しない。**

- map#6 削除対象の行 → `#a89f028e-...`（UUID id・再生不能）
- map#6 共有解除メニューの展開 → `div:nth-of-type(3) li:nth-of-type(2) > button`（aria/text 無し・多段(2階層以上) nth-of-type）
- （一覧行の座標クリック `offsetX:1268` 依存 等があれば列挙）

## 未確定（後段で確定）

- **オラクル HOW**: 「共有成立」をどの要素・表示で確認するか（録画からは確定不能・ライブ探索で確定）
- **実データのパラメタ化**: `tomomi@example.com` 等の実メールをそのまま commit しない方針（後段で確定）
```

完了したら、正規化した意味ステップ数・happy path のコア範囲・**要修復セレクタの一覧**・「未確定（Step2 進行判定）」4項目の確定/未確定を要約してユーザーに伝え、次の `e2e-spec`（Step2）へ渡せる状態であることを示す。**plan.md を出したらこの Step は完了**——ライブ探索・コード生成へは進まない。
