# Step2: シナリオ仕様化（e2e-spec）

遷移マップを「経路の羅列」ではなく「**観測点つきの検証仕様**」へ変える。中間観測点が後の漏れ分析（Step4の失敗分類）に効く。

前提: `e2e/plans/<feature>.md` に「遷移マップ」セクションが存在すること（無ければ先に `e2e-map` を実行）。**入力元が `e2e-record`（録画起点の代替 Step1）の場合、plan 内の「5観点係留メモ」「要修復セレクタ」「未確定オラクルHOW」を参考にする。**

## 認証の扱い（前提条件 vs シナリオ）

認証必須アプリでは、ここを取り違えると作成者が迷う。次のルールで固定する。

- **認証は「前提条件」がデフォルト。** ログイン済みであることを各シナリオの `開始状態` に `storageState=<role>` として書く。**ログイン操作（email入力→submit）をシナリオの操作列に書かない。** 実体は Step3 の `auth.setup.ts` が用意する（e2e-codegen 参照）。
- **ログインフロー自体の検証を作るのは form（email+password）認証のときだけ。** ログイン成功（happy）・検証エラー・認証失敗（401）・必要ならロックアウトを「ログイン」シナリオ群としてまとめ、これらは未ログイン開始（`storageState=なし`）で書く。
- **SSO / OTP / 2FA / magic link の場合は、ログインフローのシナリオを作らない。** 外部IdP のログイン画面は自動化ブラウザでは bot 検知で弾かれ、安定した検証にならない（自分のアプリの責務でもない）。認証は前提条件として `storageState` で与えるだけにし（Step3 は CDP 接続でログイン済みセッションを採取／e2e-codegen 参照）、`happy path`/`validation error` クラスは「ログイン」ではなく**ログイン後の対象機能**で1件ずつ起こす。`認証:` 欄が form 以外なら、必須の基本7観点の「ログイン成功/検証エラー/401」は **「該当なし（SSO のためログインフローは検証対象外）」と明記**する。なお未ログインで保護URLへアクセスしたときの**ログイン画面へのリダイレクトは permission差分として1件持つ**（これは IdP ログインの自動化ではないので SSO でも書ける）。
- **permission差分クラスは role ごとの storageState に対応づける。** 「一般では非表示／管理者では表示」を、`開始状態: storageState=user` と `storageState=admin` の対比として表現する。未ログインで弾かれる導線（ログイン画面へのリダイレクト等）も permission差分として1件持つ。

## 破壊的シナリオの扱い（この Step の中心責務）

中心原則: **出発点はそのプロダクトを価値たらしめている中心フロー**。価値を通すために破壊的操作（作成/更新/削除/送信など）が必要なら、それはシナリオに含めて当然であり、**破壊的かどうかは経路の属性にすぎない**。破壊的だから除外、ではない。**除外は対等な既定ではなくオプトアウト**で、結果的に破壊的なシナリオがあったときユーザー確認が一度入るだけ。

### 既定は「自己完結シナリオ」

- 価値シナリオは **自己完結（setup → 検証 → teardown）で既定作成**する。自己完結テストは**自分でデータを作り、自分で消す**ので、永続的な汚染を残さない。
- ユーザーが明示的に「これは作らないで」と言ったときだけ除外する。黙って落とさない。
- **「捨て環境かどうか」は本質ではない。** 自己完結テストは作成と削除を自分で完結させるので、向け先（捨て環境か本番類似か）は実行時のユーザー判断に委ねる。シナリオ仕様の段階で捨て環境を必須要件にしない。

### 破壊的シナリオを検出したら「一括提示」する

遷移マップの破壊性属性（Step1 で記録）を見て破壊的シナリオを検出したら、**一括で提示**してユーザーに諮る。1件ずつ逐次質問しない。

- 破壊的シナリオを**表で列挙**し、各行について「**自己完結 / 除外**」を**一度にまとめて決定**してもらう。
- 提示する選択肢は **「自己完結」or「除外」の2択のみ**。「読み取りのみに変える」「skip ガードで眠らせる」は選択肢にしない（価値フローを検証しないテストは負債になる）。
- 捨て環境 path など実行時に必要な情報があれば、その場（一括提示時）でまとめて受け取る。
- 同じ表に「**準備経路 / teardown 経路**」列を持たせ、検証対象でない前提データの経路もここで一度に確定する（下記「前提データの準備経路もここで確定する」）。

| 破壊的シナリオ | 破壊性 | teardown 可否 | 準備経路（提案） | teardown 経路（提案） | 既定 | 決定（自己完結/除外・経路） |
|----------------|--------|---------------|------------------|-----------------------|------|------------------------------|
| タスク作成→完了 | 作成/更新 | 可（UI で削除） | `ui`（作成 UI が検証対象・確定） | `ui` | 自己完結 | |
| タスク削除 | 削除 | 可（作成→削除を1本に） | `api`（削除対象は検証対象外・投入手段あり） | `api`（削除 UI 自体は `END` で検証。本文が途中で落ちたときの回収経路が api） | 自己完結 | |
| 招待メール送信 | メール送信 | 不可（外部副作用） | `api`（招待先ユーザーは検証対象外） | `none` | 要慎重 | |

### 前提データの準備経路もここで確定する（データ経路の HITL 規則）

一括提示表の「準備経路 / teardown 経路」列は、各シナリオの `data` 行（`setup` / `teardown`。語彙は下記「data メタ」）の元になる。次の規則で埋め、**質問すべきものだけ**を承認ゲート①で人に確定させる。

- **作成/削除の UI 経路自体がシナリオの検証対象（価値フローに含まれる）なら `ui` で確定し、質問しない。** 例: 「タスク作成→完了」の作成、「タスク削除」の削除。UI を踏むこと自体が検証なので、api/db に置き換える余地がない。
- **検証対象でない前提データ**（削除シナリオの削除対象・一覧に N 件必要な既存行・permission差分の対向データ等）は、表の「準備経路 / teardown 経路」列に提案値を入れて**承認ゲート①で人に確定させる**。1件ずつ逐次質問しない（一括提示表の列として一度に決める）。
- **提案値の既定**: Step1（遷移マップ「前提データ / 環境」）の「投入手段」が有る（テスト用 API / DB 接続 / seed スクリプト等）なら `api` / `db`（あるものに合わせる。**「seed スクリプト」は能動的にデータを投入する手段なので `db` に写す**）、無ければ `ui`。「投入手段=未確認」なら `ui` を仮置きし「要確認」を残す（「未確認項目の繰り越し」参照）。`data.setup=seed` は投入手段の有無と無関係に「既に存在する固定データを読むだけ」のシナリオ専用で、Step1 の「seed スクリプト」とは別物。
- **UI で前提データを準備してよい条件は2つだけ**: その UI 自体が検証対象であるか、api/db 経路が無いか。どちらでもないのに `ui` で準備するのは並列干渉と実行時間の主因になるので避ける。
- **無人オーサリング**では質問できないので、検証対象でない前提データも `ui` のまま置き、除外事項に「データ経路 要確認」と残して承認ゲート①へ送る。`status` はこれだけでは落とさない（`ui` は Step3 がそのまま実装できる既定値であり、承認時に人が `api`/`db` へ差し替えればよい）。

> プラグインは api/db の実体を持たない。`api`/`db` 経路の実装（`request` fixture／プロジェクト提供のスクリプト）は Step3 がプロジェクト側の手段で書く。Step2 は経路を決めるだけで、Step3 はそれに従う。

### 無人オーサリング時（ユーザーに確認できない場合）

- **その場でユーザーに確認できない状況で新規に書く**なら、破壊的シナリオは**除外し「要確認」と明示**する。負債になる未検証の破壊的テストを盲目的に書かない。
- ここでの「除外」は**シナリオ枠ごと消すことではない**。シナリオの枠（開始状態・操作・想定 teardown まで）は書き残し、状態を **「要確認（無人除外）」= `coverage` の `status=needs_review`** と明記して**承認ゲート①へ送る**（人が「自己完結」を承認したら `status=active` に上げて有効化、という申し送りにする）。枠ごと削除すると、何を確認すべきかの手がかりが失われる。**ただし承認前（`needs_review`）のものは「有効なテスト」として数えない**（コード生成 Step3 はこれを生成しない／`/e2e-audit` は優先 gap 一覧に集約する）。
- 区別は「**人がいる場でのオーサリング vs 無人でのオーサリング**」。一度人と検証済みの破壊的テスト（teardown が確認済み）は、CI で無人実行してよい。無人で禁じるのは「未検証の破壊的テストを新規に書く」ことであって、検証済みテストの実行ではない。

### 不可逆な副作用は人がいても慎重に

- teardown 不能な副作用（**課金・実メール送信・外部通知**など）は、人がいても**除外**するか、**明示的合意**のもとで慎重に扱う。自己完結化できない（消せない）破壊は既定で除外に倒す。

## 基本7観点（最低1件ずつ必須）

遷移マップから、以下の **基本7観点を最低1シナリオずつ** 起こす。対象機能に存在しない観点は「該当なし（理由）」と明記する（これは強制チェックリストで、`/e2e-audit` の gap 検出がこの強制性に依存する）。WebアプリE2Eの「標準分類」ではなく、実際に壊れやすい所を押さえる実務観点で、下記5階層に整理できる。各観点の `class` slug は機械可読契約（`@class:<slug>`）なので語彙は固定。

**1. 価値フロー**
1. **happy path**（`happy`）— 価値が成立する主経路（正常系）。

**2. 入力・業務ルール**
2. **validation error**（`validation`）— 入力検証・業務ルール違反。必須/形式/範囲/重複など。

**3. 権限・セキュリティ**
3. **permission差分**（`permission`）— 権限による表示/操作の差。例: 未ログイン / 一般 / 管理者 / **所有者・テナント違い**（他人のリソースを操作できないか）。

**4. ブラウザ/ページライフサイクル**
4. **戻る操作**（`back`）— history/bfcache/session/cache を含む状態復帰。ブラウザ戻る・キャンセルでの復元。例: **ログアウト後に Back/cache で機密情報へ戻れてしまわないか**（OWASP）。
5. **再読込**（`reload`）— リロード後の状態保持/喪失。例: hydration / 再取得 / 入力保持 / **直URL（ディープリンク）復元**。
6. **途中離脱**（`abandon`）— フォーム入力途中の離脱・再訪。例: 未保存 / 中断 / キャンセル / **離脱警告(beforeunload)**。

**5. 非同期・ネットワーク耐性**
7. **ネットワーク遅延**（`network`）— 遅延/失敗時のローディング・disable・二重送信防止・リトライ・エラー表示。**「遅延」ではない失敗応答（server error / API failure）もこの観点で拾う**。

### 補助観点（任意・該当時のみ・強制しない）

下記は基本7観点には含めない**任意**の観点。**該当する機能のときだけ**1件足せばよく、**「該当なし」は書かない／`class` slug にも含めない（`/e2e-audit` のカウント対象外）**。

- **a11y / keyboard navigation** — キーボード操作のみで主経路を完遂できるか、フォーカス順・role/label が妥当か。
- **session timeout / logout** — 操作中にセッションが失効した場合の振る舞い（ログイン誘導・未保存データの扱い）。※「戻る操作」の logout-Back 例とは別 facet（こちらは操作中の失効）。

> browser compatibility（クロスブラウザ）は本ワークフローの範囲外。Playwright config の project（chromium/firefox/webkit）で担保する設定責務であり、シナリオ観点としては起こさない。
> data integrity / teardown は、破壊的シナリオの必須項目「後始末（teardown）」（下記）でカバー済み。

## 各シナリオの必須項目

| 項目 | 内容 |
|------|------|
| ID | `S<n>`（S1, S2, …）の連番。シナリオ見出しに必須採番。**Step3 が test タイトルに `[S<n> / map#<m>]` として埋め込み、Step4 の Coverage Matrix が逆引きする** ので飛ばさない |
| coverage | 横断 audit（`/e2e-audit`）が機械的にパースする `class` / `role` / `status` / `exec` の4フィールド。**正本はこの plan**。Step3 が同じ値を Playwright の `tag` に mirror し（`@class:` / `@role:`、`exec=heavy` のときだけ `@heavy`）、`/e2e-audit` が plan とタグのズレを「未突合」として検出する。下記「coverage メタ」参照 |
| data | 前提データの **準備経路（`setup`）・所有（`own`）・後始末経路（`teardown`）** の3フィールド。破壊的シナリオの一括提示表（準備経路 / teardown 経路列）で確定した値をここに写す。前提データが不要なら `setup=none / own=self / teardown=none`。下記「data メタ」参照 |
| 遷移マップ参照 | このシナリオが導出された遷移マップ行の `#`（例: `map#2` / 複数なら `map#2,#5` / 該当無しは `map#-`）。遷移マップの `#` は Step1（e2e-map）の表で必須採番されている前提 |
| 開始状態 | ログイン状態・データ前提・URL |
| 開始状態の確認（precheck） | 開始状態が実際に成立していることを示す**可視シグナル**（前提データの行が存在する・ログイン済みのランドマークが出ている・書き込みスコープ＝ユニーク名/実行IDの対象が 0 件である、など）。観測点 ID は `PRE`。**破壊的シナリオでは必須**、それ以外も最低限「ログイン済みランドマーク」を1つ書く。Step3 が `test.step('S<n>-PRE …')` として先頭で assert し失敗メッセージに `[precheck]` を付け、Step4 は `[precheck]` 失敗を「前提データ不整合」へ機械分類する（アプリの不具合と環境側の不備を切り分ける） |
| 操作 | ユーザー操作の列（番号付き）。番号がそのまま観測点 ID `O<k>` |
| 中間観測点 | 操作の途中で確認すべき状態（ローディング表示・URL変化・トースト等）。**`CP1`, `CP2`, … と採番必須**（観測点 ID `CP<k>`） |
| 終了条件 | 成功とみなす最終状態（success criteria を曖昧にしない）。観測点 ID は `END` |
| 後始末（teardown） | **破壊的・自己完結シナリオのみ必須**。作成したデータを何でどう消すか（同じ UI 経路で削除など）。経路は `data` 行の `teardown` と一致させる。非破壊シナリオは `-`。 |
| 除外事項 | このシナリオで検証しないこと。`exec=heavy` の判定根拠、「データ経路 要確認」もここに1行で残す |

> **観測点 ID（`PRE` / `O<k>` / `CP<k>` / `END`）は plan↔trace の手順粒度トレーサビリティの契約。** Step3 が `test.step('S<n>-PRE …')` / `('S<n>-O<k> …')` / `('S<n>-CP<k> …')` / `('S<n>-END …')` に mirror し、Step4 が step 名で plan の観測点と機械突合する（Coverage Matrix の「中間観測点 assert」列を人手判定にしない）。ID を飛ばす・重複させると突合が壊れる。

### coverage メタ（横断 audit 用の機械可読フィールド）

各シナリオに `coverage` 行を1本必ず持たせる。これが横断 audit（`/e2e-audit`）の入力契約で、**plan が正本**。Step3（e2e-codegen）が同じ値を Playwright の `tag` に mirror し、`/e2e-audit` が `plans/ tests/ reports/` をスキャンして feature 横断の不足（class の穴・role の穴）を `e2e/index.md` に派生集約する。**この plan が唯一の正本で、台帳（coverage.yml 等）は持たない**（同じ事実を二重持ちして drift させない既存方針の延長）。

書式（シナリオの先頭フィールドとして1行）:

```markdown
- **coverage**: class=`happy` / role=`guest` / status=`active` / exec=`light`
```

- **class**（基本7観点の slug・必須）— 下記7観点に対応する固定語彙（監査では「class」として集計する機械可読契約語）。Step3 が `tag: '@class:<slug>'` に mirror し、audit が class×gap で集計する。

  | class slug | 基本観点 |
  |------------|-----------|
  | `happy` | happy path |
  | `validation` | validation error |
  | `permission` | permission差分 |
  | `back` | 戻る操作 |
  | `reload` | 再読込 |
  | `abandon` | 途中離脱 |
  | `network` | ネットワーク遅延 |

- **role**（対象ロールの slug・必須）— そのシナリオが前提とする `storageState` に対応する slug。未ログインは `guest`、以降はプロジェクトのロール名に揃える（`user` / `admin` など。`開始状態` の `storageState=<role>` と同じ語）。Step3 が `tag: '@role:<slug>'` に mirror し、audit が role×gap で集計する。permission差分のように1シナリオで複数ロールを対比するなら主たるロールを書き、対の役は除外事項/中間観測点で補う。
- **status**（4値・必須）— シナリオの取り扱い状態。**既存語彙の formalize**であり、新概念は `covered_elsewhere` の1つだけ。

  | status | 意味 | 既存対応 |
  |--------|------|----------|
  | `active` | spec 生成対象（自己完結確定／非破壊の通常シナリオ） | 通常シナリオ |
  | `excluded` | ユーザーが明示的に除外したシナリオ | 既存「除外」 |
  | `needs_review` | 承認前・未確認。**有効に数えない**（Step3 は生成しない） | 既存「要確認（無人除外）」と**同一視**（別概念として2つ作らない） |
  | `covered_elsewhere` | 別 feature で検証済みのため重複回避で本 feature では作らない（**新規**）。どこで検証済みかを除外事項に書く | （新規） |

- **exec**（実行制御・必須・既定 `light`）— そのシナリオをどの実行プロファイルで走らせるか。

  | exec | 意味 |
  |------|------|
  | `light` | 既定。並列・通常 timeout で走らせてよい |
  | `heavy` | 直列・長い timeout が必要。判定基準は **想定所要時間 60s 超／重い非同期やファイル往復（アップロード・生成・ダウンロード）／共有データへの書き込みで直列必須** のいずれか |

  `heavy` にするときは**判定根拠を除外事項に1行**書く（例: 「exec=heavy: PDF 生成の完了待ちが 60s 超」）。根拠が無い `heavy` は自己点検で落とす。Step3 は `exec=heavy` のときだけ `@heavy` を `tag` に mirror し、そのテストは `chromium-heavy` project（`grep: /@heavy/`・非並列・長 timeout）で走る。`light` はタグを付けない（既定 project が `grepInvert: /@heavy/` で拾う）。`/e2e-audit` は `exec` を gap 集計に**使わない**（`heavy` は穴ではない。index.md に件数列を出すだけ）。

> `route`（経路URL）と `risk`（リスク度）はフィールドに足さない。route は `開始状態` に URL が既にあり、risk は主観で drift しやすいため。audit は class/role/status の3軸だけで横断不足を出す（`exec` は実行制御であって網羅の軸ではない）。

### data メタ（前提データの経路・所有・後始末）

各シナリオに `data` 行を1本必ず持たせる（`coverage` 行の直後）。破壊的シナリオの一括提示表で確定した「準備経路 / teardown 経路」をここに写し、Step3 はこの経路に従って setup/teardown を実装する。`/e2e-audit` はこの行を集計しない（gap ではない）が、旧 plan で未付与なら「メタ未付与」として扱われる。

```markdown
- **data**: setup=`ui` / own=`self` / teardown=`ui`
```

| フィールド | 語彙 | 意味 |
|---|---|---|
| `setup` | `ui` / `api` / `db` / `seed` / `none` | 前提データの準備経路。`ui`=画面操作で作る、`api`=テスト用 API / `request` fixture、`db`=DB 接続・プロジェクト提供スクリプト、`seed`=固定シードを読むだけ（作らない）、`none`=前提データ不要 |
| `own` | `self` / `shared` | `self`=本シナリオが自分で作る（ユニーク名/実行IDで専有）。`shared`=既存データを読む。**`shared` に書き込む場合は理由を除外事項に書く**（並列衝突候補なので `exec=heavy` にするか、`self` 化を検討する） |
| `teardown` | `ui` / `api` / `db` / `none` | **失敗時にも走る後始末（回収）経路**。本文の UI 削除が検証対象（`END` で消滅を検証）でも、本文が途中で落ちたときに `setup` で作ったデータを誰が消すかをここに書く——`setup=api`/`db` なら通常 `teardown` も同じ経路（Step3 は 404 を許容する冪等な後始末を書く）。`ui` は「作成した UI 経路で削除する」自己完結シナリオ。非破壊・`seed`・`none` 準備のシナリオは `none` |

- 語彙は固定（自由記述にしない）。「同じ UI 経路で削除」のような説明は「後始末（teardown）」欄に書き、`data` 行は語彙だけにする。
- `setup=ui` が許されるのは「その UI 自体が検証対象」または「api/db 経路が無い」ときだけ（前節の HITL 規則）。

### 件数系の観測点・終了条件は「自分が作ったデータのスコープ」で書く

「一覧の項目が1件だけ増える」「一覧の件数が開始時に戻る」のような**件数系**を、**総件数の before/after** として書かない（環境を専有できる場合を除く）。並列ワーカーや他の利用者が同じデータ空間を触るため、総件数の差分は**本質的に flaky** で、Step3 は結局それを実装できない。結果として Coverage Matrix に恒久的な「部分」が積もる（実運用で発生）。

代わりに、**そのシナリオが作ったデータのスコープ**で表現する——ユニーク名・実行ID・完全一致による「対象が1件だけ存在する」「対象が0件になる」。二重作成の検出も、総件数ではなく「**既定名／対象名の行がちょうど1件**」で書ける。**spec が検証できない終了条件を plan に残さない。**

### 遷移マップの「未確認」項目の繰り越し

遷移マップで `確認状況=未確認` の観測点・分岐・状態（例: ローディング表示の有無、入力途中値の保持仕様）は、**推測で終了条件を断定しない**。中間観測点・終了条件にその不確実性を**「未確認・要確認」と明記**したまま残し、承認ゲート①へ送って人に確定させる。`success criteria を曖昧にしない` の原則は「未確認なのに確定したふりをしない」と両立する——曖昧さを**隠さず明示する**のが正しい。挙動が二択に割れる場合（保持する/しない等）は両ケースを記し、「いずれでも UI が壊れない」を最低ラインに置いてよい。

遷移マップの「前提データ / 環境」で **`投入手段=未確認`** のときも同じ扱いにする。`data` 行は `setup=ui` / `teardown=ui` を仮置きし、除外事項に「データ経路 要確認（投入手段が未確認）」と残して承認ゲート①へ送る。人が投入手段を確定したら `api`/`db` へ差し替える。

## 自己点検リスト（成果物を書き終えたら通す）

plan を承認ゲート①へ出す前に、active なシナリオ全件について次を機械的に確認する。引っかかった項目は直すか、除外事項に理由を残す。

- [ ] 各シナリオの `data.own` が `self` か。`shared` なら**読み取りのみ**か（書き込むなら理由が除外事項にあるか）。
- [ ] `shared` に**書き込む** active シナリオが2件以上、同じ対象（同じ行・同じ設定・同じアカウント状態）を触っていないか。あれば片方を `self` 化するか、両方を `exec=heavy` にして直列化する。
- [ ] 各シナリオの開始状態が、**他シナリオの終了状態に依存していない**か（実行順序に依存する plan は並列で壊れる）。
- [ ] 件数系の観測点・終了条件が**自スコープ**（ユニーク名/実行ID/完全一致）で書かれているか（上記「件数系の観測点・終了条件は『自分が作ったデータのスコープ』で書く」）。
- [ ] 中間観測点が `CP1..` で採番され、`開始状態の確認（precheck）`（`PRE`）が全シナリオにあるか（破壊的シナリオは前提データ・書き込みスコープまで、非破壊は最低限ログイン済みランドマーク）。
- [ ] `exec=heavy` に判定根拠が1行あるか。根拠が無ければ `light` に戻す。
- [ ] `setup=ui` のシナリオは「その UI が検証対象」か「api/db 経路が無い」かのどちらかに該当するか。該当しないなら `api`/`db` 提案に変えて一括提示表へ載せる。

## BDD が必要なチーム向け（任意）

BDD文化のチームは、各シナリオを Gherkin `.feature` にも転記できる（Given=開始状態, When=操作, Then=終了条件, 中間観測点は And で挟む）。ただし二重管理になるため、**Markdown plan を正本**とし `.feature` は派生物として扱う。

完了したら全シナリオを一覧で要約し、**破壊的シナリオの一括提示で確定した「自己完結/除外」の決定**と**検証対象でない前提データの準備経路 / teardown 経路（`data` 行）の提案**も添えて、**承認ゲート①**（オーケストレーター側）でユーザーのレビューを促す。コード生成（Step3）は承認後に行う。Step3 はここで確定した方針（自己完結なら teardown 込み、除外ならその旨、`data` の経路、`exec` の実行プロファイル）に従うだけで、勝手に skip ガードで黙らせない。
